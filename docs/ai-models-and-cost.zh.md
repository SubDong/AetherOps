## 服务商配置

每个账号在 `ai_config` 里维护自己的一套配置（主键 `(owner_id, id)`），每条包含 provider、base URL、
模型名、API Key、temperature、max tokens、`enabled`、`sort_order`、`cost_tier`、`cost_tier_source`、
`price_in`、`price_out`。

界面上提供的服务商：**OpenAI**、**Anthropic (Claude)**、**腾讯云**、**Azure OpenAI**，以及**自定义**。
「自定义」的意思是你贴任何 OpenAI 兼容的 Base URL 和模型名 —— DeepSeek、Qwen、vLLM/Ollama 网关、内部代理
都是这样接进来的。Key 静态加密后存储（`enc:v1:` AES-256-GCM，密钥在数据目录），且永远不会出现在非本人的视图里。

配置上的**测试**按钮会真的发一次补全请求，所以 Base URL 打错字会在你烧掉一轮对话之前被发现。

## 模型选择 auto 模式

模型选择器里有一个虚拟条目 `auto`（`AUTO_MODEL_ID`），它不是 `ai_config` 里的一行。某一轮以 `auto` 模式
执行时，服务端会在本地给这次请求打分，再把分数映射到你的某套配置的成本档位上。

```
tier = clamp(1 + min(score, 4), 1, 5)
```

打分信号（每项贡献 1–2 分，累加）：

| 原因标签 | 触发条件 |
|----------|----------|
| `long-prompt` / `medium-prompt` | 指令长度 —— 长指令通常意味着多步骤工作 |
| `has-code` | 消息里有代码块或脚本 |
| `wants-action` | 用的是让 Agent *去做*、而不是去解释的动词 |
| `troubleshooting` | 报错 / 异常 / 故障类词汇 |
| `large-context` | 附带了很长的终端输出 |
| `deep-tool-chain` | 这个会话已经发起过若干次工具调用 |
| `long-conversation` | 存储的历史消息很多 |
| `short-question` | 什么都没命中 → 档位 1，也就是最便宜的那套配置 |

选定目标档位后，具体配置按 `|profile.costTier − targetTier| + healthPenalty` 取最小值，平分情况下偏向
**更便宜**的那一套。选中的配置、分数与原因都会记日志（`tier=3 score=4 pick=... reasons=...`）并展示出来，
好让你看清为什么跑了这个模型。

**健康惩罚**用的是最近 `ai_usage` 行统计出的逐模型成功率：样本至少 5 条时才生效，一个总在失败的模型会被
从选择里推开。不足 5 条样本时不加惩罚，否则一次失败就等于「100% 失败率」。

刻意**没有**实现的东西：「问一个小模型该用哪个模型」。那要多花一次 API 调用，而这次调用往往比它省下的 token
更贵。这里的路由是零额外调用。

## 成本档位及其来源

`cost_tier` 是 1（最便宜）… 5（最强），`cost_tier_source` 记录这是谁定的：`auto`（推导得出）或 `manual`
（你手工设定）。这一列的存在理由是：没有它，每次保存都会覆盖掉你刻意钉住的档位。

档位推导（`ai-cost-analyzer.ts`），优先级从高到低：

1. **定价目录** —— 如果这条配置有价格（或能查到价格），就把它在你**自己其余配置中的相对位置**排出来。
   相对排名才是要点：绝对阈值在厂商降价那一刻就过期了，而 `auto` 需要知道的只是「你手上这几个里哪个更便宜」。
2. **模型名规则** —— 面向不在目录里的网关/私有化部署，做粗粒度的家族启发式判断。
3. **保持不变** —— 前两条都不成立时，沿用已有值。猜出来的档位会让 `auto` 把钱花在错误的模型上，这比没有档位
   更糟。

如果你配了四个模型却从没设过档位，它们会全部停在默认值 3，于是 `auto` 每次都解析到同一个（在距离相同的目标里
按 `sort_order` 取第一个）—— 界面会显示「auto」，但什么都没省。这种静默失效正是上面这套推导要防的事。

## 定价目录

`server/service/ai-pricing.ts` 拉取 OpenRouter 的公开模型目录
（`https://openrouter.ai/api/v1/models`，不需要 API Key），从中提取每 100 万 token 的输入/输出价格。

它遵守三条规则，在受限网络里运维时这几条尤其要紧：

1. **绝不阻塞主流程。** 离线、被封、超时 → 得到空目录，档位退化为名称规则，成本显示为*未知*而不是 0。
   编出来的成本比没有成本更坏。
2. **成功缓存 24 小时，失败缓存 5 分钟**，这样保存配置不会每次都触网。
3. **名称撞车时取更贵的那一条** —— 估算要往高了偏，否则你会以为自己正在省钱。

超时 8 秒，响应上限 8 MB，服务商前缀映射把你的 provider 对到目录里的 ID（Azure 沿用 OpenAI 的命名；
`custom` 按模型名匹配）。出站请求清单见 [README § 对外网络请求与隐私](../README.zh.md#对外网络请求与隐私)。

## 用量记账

每次完成的 LLM 调用写入一行 `ai_usage`：

| 列 | 含义 |
|----|------|
| `owner_id`、`chat_id`、`connection_id` | 谁、哪次对话、在哪台主机上干活 |
| `model_id`、`model_label` | 跑了哪套配置 |
| `auto_routed` | 是否由 `auto` 选中（这样你才能衡量 auto 实际做了什么） |
| `prompt_tokens`、`completion_tokens`、`total_tokens` | 取自 `done` 事件里服务商返回的 `usage` |
| `cost_usd` | **写入当时**用那一刻的价格算出来 |
| `ok` | 失败的调用同样记录 —— 健康惩罚就是从这里来的 |

几处刻意为之的细节：

- 成功但响应里没有 `usage` 的调用**不记录**：一条 0 token 的记录会拉低均值，让「节省额」失去意义。
- 成本在写入时冻结。厂商价格会变，而你实际付过什么的历史不应该跟着变。
- 如果某套配置存的价格是 null（保存时目录还没加载成功），写入时会再回到内存目录里查一次价格，这样面板不会
  报出一个假的 $0。
- 记账失败会被吞掉并打一条警告。记账的问题不该打断你的对话。

## 预算

每个账号一行 `ai_budget`，三个上限，`0` 表示不限：

| 上限 | 校验对象 | 超限返回码 |
|------|----------|------------|
| `chatTokenLimit` | 本次对话累计 token | `chat-token-limit` |
| `dailyTokenLimit` | 本地零点以来累计 token | `daily-token-limit` |
| `dailyCostLimit` | 本地零点以来的美元成本 | `daily-cost-limit` |

校验发生在调用**之前**，超出上限时向界面发一条显式的错误事件（带具体数字，例如 `(182340/200000)`），
而不是静默截断。如果预算行读不出来，则放行这一轮并记一条警告 —— 预算表坏了不该把 AI 功能一起拖下线。

想要的是按日**提醒**而不是硬上限的话：目前没实现。请看成本面板，或者自己查 `ai_usage`。

## 成本洞察与节省额

洞察接口（`getCostInsights`）返回：

- 当日合计，以及当日按模型拆分的 `byModel`；
- 当前对话的合计；
- 该账号的预算行；
- `baselineModel` —— **你自己拥有的、单价最贵的那套已定价配置**；
- `savedUsd` —— `(同样的 token 按基准价计算) − (今天实际花费)`，即「如果今天每一轮都打给你最贵的那个模型，
  会花多少」；
- `partial` —— 当部分调用没有已知价格时为 true。此时请把当日合计当作**下限**，不是一个精确数字；界面必须
  这么标注，而不是把一个低估值当事实呈现。

## 非 Agent 对话

普通问答（`chat()`，不带工具）按偏好解析配置：你指定的模型若可用就用它，否则选**按档位最便宜的可用配置**。
一段只是在解释什么的对话，没有理由花档位 5 的钱。

## 给贡献者的设计说明

- 路由逻辑保持本地、确定、可解释。原因列表要完整保留 —— 一个用户无法审计的 `auto` 模式，跟一个坏掉的
  `auto` 模式长得一模一样。
- 绝不用 `0` 代替未知价格，绝不静默选一个档位。
- 新模型/新服务商：扩充 `ai-pricing.ts` 里的「服务商 → 目录前缀」映射，而不是在界面里硬编码价格。价格属于
  目录查询这条链路，因此它应当随目录一起过期。
- 如果你要再加一个逐次调用的副作用：放在响应转发之后，并把它的异常吞掉。用户这一轮比账本重要。
